# Part A: Driftwood build (full-stack document copilot)

## A1. Read the client brief and inspect the data

1. **Goal:** Understand the problem (analysts spend about half their week on filing intake) and get a real dataset before coding anything.
2. **Created/modified:** The `data/` folder with downloaded filings (by ticker and year) and a `manifest.json` index (ticker, filing date, local path). `download.py` already existed in the starter repo.
3. **Tools/commands:** From the `data` folder, `uv run` on `download.py`. Python run through uv. Viewed an `.htm` file in the editor's browser preview.
4. **Why:** "Begin with the data". It shapes every later choice, and the brief makes grounded, cited answers the product requirement.
5. **Expected:** Five tickers (Apple, Microsoft, Nvidia, Amazon, Google), five years each.
6. **Verified:** Opened Apple's 2021 filing and scrolled. It is a huge document full of tables.
7. **Errors/limits:** `.htm` was unfamiliar to him ("a kind of HTML but not really"). The risk he names is hallucinated facts across many years.
8. **Before PaperPilot:** Download and eyeball a few real papers (PDFs, not just abstracts) before designing. Look at tables, equations and two-column layout, since parsing them will drive your quality problems.

## A2. Prepare the repo, conventions and checklist

1. **Goal:** Give the AI agent enough standing context to make good decisions.
2. **Created/modified:** Monorepo with backend and frontend folders. `agents.md` files at the root, backend and frontend (already in the starter). An architecture document and a `to-dos.md` checklist (the latter generated by the AI on request). Created a `development` branch so `main` stays the starting point.
3. **Tools/commands:** Cursor with an agent. He asked it for a checklist of the most logical build order. Dictation tool for prompts.
4. **Why:** "The better the initial prep work, the faster you can go with agents." A monorepo lets the agent see both halves.
5. **Expected:** A phased checklist to work through.
6. **Verified:** Previewed the checklist and accepted it ("we actually start with a database and sample the data").
7. **Errors/limits:** None. The architecture document is never shown, only narrated.
8. **Before PaperPilot:** Write the equivalent `agents.md`/`CLAUDE.md` and a phased checklist first. Keep it short. Both transcripts treat these files as the highest-leverage prep.

## A3. Create the Supabase project and configure environment files

1. **Goal:** A hosted database and auth service, plus all keys wired in locally.
2. **Created/modified:** Supabase project "driftwood capital", region Europe, **automatic RLS enabled** at creation. Env files copied from `.env.example` for frontend and backend. Frontend needs: API base URL, Supabase URL, anon (publishable) key. Backend needs: Supabase URL, publishable key, service-role key, database URL, OpenAI key.
3. **Tools/commands:** Supabase dashboard (Connect → **session pooler** string), OpenAI platform for an API key, a password generator.
4. **Why:** Same-region services avoid latency. RLS makes the public anon key safe to ship in the browser.
5. **Expected:** Services can all authenticate to each other.
6. **Verified:** Checked that only `to-dos.md` showed as changed in version control, which proves env files are ignored.
7. **Errors/limits:** A password with special characters broke env parsing (the `#` and `%` characters). He reset the password, then wrapped the database URL in quotes. He also caught himself pasting real credentials into the **example** file and corrected it. Secrets were shown on screen on purpose; he says he will delete them.
8. **Before PaperPilot:** Pick the URL-safe password up front, or quote the connection string. Keep the service-role key backend-only. Check `.gitignore` before the first commit.

## A4. Backend scaffold

1. **Goal:** A running FastAPI app that loads settings and proves imports work.
2. **Created/modified:** `backend/pyproject.toml` (dependencies, an exclude-newer-than-7-days setting, hatchling package config naming `app` as importable), `app/config.py` (pydantic-settings), `app/main.py` with a health/status endpoint, a short backend README.
3. **Tools/commands:** `uv sync`, `uv add` with the dependency list copied from the backend setup guide, `uv add` for dev dependencies (pytest, ruff, and ipykernel), `uvicorn` with `app.main:app` and reload, run through uv. Cursor's interpreter path set manually.
4. **Why:** Establish the config pattern and Python path layout before adding features.
5. **Expected:** `Settings` imports cleanly, and the status endpoint answers.
6. **Verified:** Imported the settings object. Removed a required variable and confirmed a validation error. Started uvicorn and hit the status endpoint in the browser.
7. **Errors/limits:** Editor showed unresolved imports until the interpreter path was set. Imports failed until `app` was declared as a package in `pyproject.toml`. He notes the env file location is a path issue he will revisit ("it depends where we import this from").
8. **Before PaperPilot:** Settle the Python packaging and import path on day one. Scripts outside `app/` will hit this again.

## A5. Database models and first migration

3. **Tools/commands:** AI prompts from the checklist. Alembic with a preview-before-apply flow, then apply.

He questioned `message_citations`, asked the AI to justify it, and kept it. He also first noticed he had no commits and started committing here.
8. **Before PaperPilot:** Decide on pgvector dimension and index at this step (it is expensive to change later). Think about what a "paper", "section", "finding" and "citation" row look like before generating models.

## A10. Convert filings to markdown (Docling)

## A12. Chunk and embed

1. **Goal:** Searchable chunks with embeddings and page/section info.
2. **Created/modified:** An `ingest` script set: a chunking file, an `embeddings.py`, and an orchestrator. Inserts into `document_chunks`.
3. **Tools/commands:** Asked for a **plan** first, with an explicit instruction not to run anything. Docling HybridChunker (hierarchical, tokenizer-aware) sized to the embedding model's token limit. OpenAI embeddings (`text-embedding-3-small`).
4. **Why:** Retrieval needs chunk-level units. Header-aware chunking beats naive splitting.
5. **Expected:** Chunks with document id, index, page number, section, text, token count, embedding and a text-search column.
6. **Verified:** The plan included a **single-chunk test** before the full run, because embedding costs money. Afterwards he inspected rows in Supabase and checked the OpenAI usage page (about 11 cents, with lag).
7. **Errors/limits:** He agreed to rebuild the Docling document from the original HTML (not the markdown) so page numbers survive. Table chunks have "very little context", so he expects poor semantic search there. Chunk quality "can take weeks". A chunk-summary idea is parked.
8. **Before PaperPilot:** Always test one document end to end first. Store page number and section on each chunk from day one, since citations depend on it.

## A13. Hybrid retrieval

1. **Goal:** Return relevant chunks using meaning and keywords.
2. **Created/modified:** A `retrieval` module of small files (Pydantic models, query embedding, SQL queries, retriever) and a README with a mermaid diagram. Config values for top K, RRF constant and neighbour radius.
3. **Tools/commands:** New chat with reset context. Linked an earlier public hybrid-search repo as a pattern, telling the AI to adapt BM25 to Postgres full-text search and to ask for a plan first. A Cohere reranker was offered by the reference and declined.
4. **Why:** Pure vector search misses exact terms. He wanted a known pattern.
5. **Expected:** Semantic and keyword candidates fused with RRF and hydrated with metadata and neighbour chunks.
6. **Verified:** A smoke script ran the Apple revenue-mix question with ticker/form filters and printed retrieved chunks.
7. **Errors/limits:** Retrieved table chunks were hard to read. The keyword half was "way too naive" because it used the whole question. Parameters are untuned defaults. Retrieval quality was judged only by eye.
8. **Before PaperPilot:** Build a tiny evaluation set of questions with known source pages before tuning anything.

8. **Before PaperPilot:** Pick the embedding model and dimension, and check index limits, before the first ingest.

## B7. Modules 3 and 4: record manager and metadata

1. **Goal:** No duplicate documents. Structured metadata for filtering.
2. **Created/modified:** Content-hash column and record-manager service. Upload logic that skips unchanged files and re-imports changed ones (delete old chunks, then re-import, his preference). Metadata extraction (LLM, Pydantic schema, first 8,000 characters), schema stored as JSON in global settings, metadata copied to chunks, expandable metadata UI.
3. **Tools/commands:** Two plan sessions in parallel, with Claude asking him questions. Build for each.
4. **Why:** Duplicates add noise. Filters narrow search.
5. **Expected:** Re-upload says unchanged. New files get a title, summary, type, topics and language.
6. **Verified:** Re-uploaded the same file: first it said "updated, reprocessing" because the hash hadn't been saved, then "unchanged, skipped". LangSmith showed what the search tool received.
7. **Errors/limits:** Duplicate database function error in search (fixed). The model passed an invented `document type` filter and got zero results. He lists this as a prompt and cautious-filter problem.
8. **Before PaperPilot:** Dedupe by DOI/arXiv id as well as file hash. Do not let the model invent filter values.

## B8. Modules 5 and 6: Docling and hybrid search

1. **Goal:** More file formats. Keyword + vector + RRF + rerank.
2. **Created/modified:** Docling pipeline in ingestion (50 MB limit in the plan). Hybrid search, RRF, Cohere reranker configured in settings.
3. **Tools/commands:** Plans for both at once. Claude warned Docling needs PyTorch (about 2 GB). Release by an agent: tag **0.5–0.6** with release notes.
4. **Why:** Real documents are PDFs and Office files.
5. **Expected:** Upload a PDF, get chunks, ask a question, see reranking in traces.
6. **Verified:** Uploaded a file, five chunks and metadata appeared. Asked a water-supply question, got a correct answer. After adding a Cohere key, LangSmith showed rerank score, RRF score and similarity (earlier run showed only RRF and similarity).
7. **Errors/limits:** Local reranker was never demonstrated. Ingesting 16 files was slow, memory hit 92% on the laptop. Claude found four problems (e.g. file loaded twice, no concurrency cap). A concurrency limit of 3, then 10, helped only slightly; the bottleneck stayed **unidentified**.
8. **Before PaperPilot:** Benchmark ingestion on 50 papers early. Decide whether parsing runs locally or as a service.

## B9. Module 7: text-to-SQL and web search

1. **Goal:** Let the agent query a structured table and the web.
2. **Created/modified:** A `sales_data` demo table, SQL tool, a **dedicated read-only Postgres role** with its own connection string, Tavily web search (key entered in settings).
3. **Tools/commands:** Plan with a design choice (query templates vs raw SQL with database-level permissions; he chose raw SQL with a locked-down user). Supabase dashboard and SQL editor.
4. **Why:** Security must be enforced by the database.
5. **Expected:** Correct totals from SQL and weather from the web.
6. **Verified:** Compared the agent's SQL result to the SQL editor. LangSmith showed the query and tool results. After the fix, delete and other-table attempts were refused. Web search worked for a weather question.
7. **Errors/limits:** The tool returned all 12 rows because a fallback ignored the query on failure, and a migration was never applied. Claude proposed an RPC function; he rejected it as unsafe and over-engineered. The connection used port 5432 instead of the pooler's 6543. The local model's context had reset to 4,000 tokens after a restart. `sales_data` ended with **RLS off** (he flags it).
8. **Before PaperPilot:** For a findings table, create the read-only role first and test destructive SQL against it.

## B10. Module 8: sub-agents and UI

1. **Goal:** A tool that analyses one whole document in an isolated context.
2. **Created/modified:** `analyze document` tool/sub-agent, nested tool-call and thinking UI, tool-call persistence (JSONB on messages), configurable max tool rounds with a dynamic prompt line, dark mode with a dark logo, system-prompt edits, `CLAUDE.md` note on remote Supabase migrations.
3. **Tools/commands:** Plan with parallel waves. Cursor agent for prompt edits. Different local and cloud models compared.
4. **Why:** Chunks lose whole-document context, and loading documents into the main agent bloats it.
5. **Expected:** Main agent searches, delegates, and shows nested steps.
6. **Verified:** Summarised a 38-page oven manual. LangSmith showed three traces (question, sub-agent, final).
7. **Errors/limits:** A search with invented filters found nothing, so he told the agent not to filter. The sub-agent errored (a Supabase client error, then "could not find the table in the schema cache"), the second tied to an unpushed migration. The tool was being passed a document id where a file name was needed. Tool calls rendered in the wrong place, vanished on completion or refresh, text duplicated between agent and sub-agent, think tags (Qwen 32B) broke bubble placement. A looping 30B mixture-of-experts model. Several of these were fixed by feeding Claude screenshots.
8. **Before PaperPilot:** Define the sub-agent's input contract (paper id, schema, question) before building the UI.

## B11. Wrap-up

1. **Goal:** Release and an honest status.
2. **Created/modified:** Final commit, tag and release for modules 7–8.
3. **Tools/commands:** Agent-driven commit and release.
4. **Why:** Rollback points.
5. **Expected:** n/a.
6. **Verified:** End-to-end smoke tests on all modules. Not exhaustive.
7. **Errors/limits:** He calls it an **alpha** and defers deployment, staging and rollback to a later video.
8. **Before PaperPilot:** Treat "demo works" and "release ready" as different gates.
